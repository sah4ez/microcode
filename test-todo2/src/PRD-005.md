# PRD 005: Аутентификация пользователей в test-todo2 (Go + tg v3)

## Контекст (стек)

Это Go-сервис на `github.com/loki/todoservice` (модуль в `test-todo2/src/`):
- **Контракты** описаны `@tg`-аннотированными интерфейсами в `contracts/` и
  `contracts/dto/`; HTTP-транспорт (fiber) **генерируется** командой
  `tg server -o internal/transport`. Новые методы добавляются В ПЕРВУЮ
  ОЧЕРЕДЬ в контракты — сгенерированный транспорт обновляется регенерацией.
- **Бизнес-логика** — в `internal/service/service.go`; **хранилище** —
  `internal/storage/sqlite/sqlite.go` (modernc.org/sqlite, чистый Go).
- **Web UI** — vanilla JS в `static/` (`index.html`, `app.js`, `styles.css`),
  раздаётся как `//go:embed static/*` в `main.go`. Сервер слушает
  `0.0.0.0:8000`.
- Уже есть: `PersonalProfileService` (`/personal-profile` CRUD) и `TodoService`
  (`/todos`, скоуп по `x-lk-id` header). Todo несут `lk_id`.

Все новые файлы — ВНУТРИ `src/` (этого каталога). Go-код собирается
`go build ./...`, тесты — `go test ./...`. Фронтенд-тесты —
`node static/app.test.js` (vanilla, без фреймворка).

## Goal

Добавить аутентификацию пользователей в существующий сервис test-todo2. Все
операции с кабинетами (ЛК) и todo становятся доступными ТОЛЬКО после входа:
аутентифицированный пользователь создаёт/переключает кабинеты и создаёт todo
в рамках своих кабинетов.

## Functional requirements — backend (Go, contracts-first)

1. **Новый контракт `UserService`** в новом файле `contracts/user.go` (+ DTO в
   `contracts/dto/user.go`), аннотированный `@tg`, по образцу существующих
   `TodoService` / `PersonalProfileService`. Методы:
   - `POST /auth/register` — self-registration (email + password). Возвращает
     пользователя (без пароля) и токены.
   - `POST /auth/login` — аутентификация по email + password, возвращает access
     и refresh JWT.
   - `POST /auth/refresh` — обмен refresh-токена на новую пару (ротация refresh).
   - `GET /auth/me` — профиль текущего пользователя (из контекста запроса).
2. **JWT**: access + refresh, время жизни настраивается через env-переменные
   (например `AUTH_ACCESS_TTL`, `AUTH_REFRESH_TTL`; разумные дефолты).
   Использовать библиотеку из Go-экосистемы (например `github.com/golang-jwt/jwt/v5`
   или аналог — добавить в `go.mod`).
3. **Пароли**: хранить ТОЛЬКО в хешированном виде (bcrypt через
   `golang.org/x/crypto/bcrypt`). Никогда не возвращать хеш в ответах.
4. **Уникальность**: email уникален в таблице пользователей (unique-индекс в
   SQLite).
5. **Soft delete**: пользователи не удаляются физически; помечаются
   `deleted_at` (или флагом). Удалённый пользователь не может войти.
6. **CSRF**: `POST /auth/register` требует CSRF-токен (например `X-CSRF-Token`
   header или double-submit cookie; токен можно выдавать на `GET /auth/csrf`
   или в форме). Документировать выбранный механизм.
7. **Защита существующих эндпоинтов**: все методы `TodoService` и
   `PersonalProfileService` требуют валидный access JWT (через middleware /
   `@tg http-headers` или сгенерированный guard). Без токена → `401`.
   Опционально: связать кабинеты с пользователем (`personal_profiles.user_id`),
   чтобы пользователь видел только свои кабинеты — если делаешь так, явно
   опиши миграцию.
8. **Rate limit** на `POST /auth/login`: настраиваемый (env, напр.
   `AUTH_LOGIN_RATE`), in-memory per-IP; превышение → `429`.
9. **Валидация силы пароля** при регистрации: минимум 8 символов, presence
   upper/lower/digit. Невалидный → `422`.

## Functional requirements — Web UI (MANDATORY)

Реализовать в `static/` (vanilla JS, без сборщика), по образцу существующего
`index.html` + `app.js`:
- **Отдельная страница `/login`** (или экран) с формой входа (email + password)
  и кнопкой «Войти». Рядом — форма/ссылка регистрации (email + password +
  подтверждение).
- **Валидация** в браузере: формат email; сложность пароля (те же правила, что
  на бэке) с подсказкой пользователю.
- **Хранение токена**: access-токен в `localStorage` (или cookie), отправляется
  в `Authorization: Bearer ...` на каждом запросе к `/todos` и `/personal-profile`.
- **Кнопка «Выйти»**: очищает токен, возвращает на `/login`.
- **Интеграция с кабинетами**: после входа виден существующий dropdown ЛК и
  todo-список (функционал PRD-003/004 остаётся работать, но за auth).

## Non-functional requirements

- Отдельная таблица `users` в SQLite (новая миграция в
  `internal/storage/sqlite/sqlite.go`, по образцу `personal_profiles`).
- Пароли в хеше, токены не логируются.
- Новые env-переменные задокументировать в `USAGE.md`.

## Deliverables (in this src/ directory)

- `contracts/user.go` + `contracts/dto/user.go` (новый `@tg`-контракт)
- сгенерированный транспорт после `tg server -o internal/transport` (новые
  `userservice-*.go`)
- `internal/service/` — реализация auth-логики (регистрация, login, refresh,
  хеширование, валидация)
- `internal/storage/sqlite/sqlite.go` — таблица `users` + методы
- `internal/transport/` — auth-middleware (guard на существующие эндпоинты)
- `static/` — форма логина/регистрации, кнопка выхода, Bearer-токен в запросах
- `USAGE.md` — новые env-переменные и curl-примеры auth
- `README.md` — секция «Аутентификация пользователей» в wiki
- `static/app.test.js` — фронтенд-тесты на форму/валидацию (расширение
  существующего файла)

## Definition of done

- `go vet ./...` и `go test ./...` — зелёные (включая новые auth-тесты)
- `node static/app.test.js` — фронтенд-тесты зелёные
- `POST /auth/register` создаёт пользователя (пароль в хеше), `POST /auth/login`
  возвращает JWT
- Запрос к `/todos` без токена → `401`; с валидным токеном → работает как раньше
- В браузере: форма входа, после входа — кабинеты/todo; кнопка «Выйти» работает
- Пароль не возвращается ни в одном ответе; rate-limit срабатывает при переборе
